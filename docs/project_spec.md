# Project specification

## Research objective

Build a reproducible computer-science prototype that turns multivariate aerospace telemetry into a verified recovery recommendation. The system must expose the reasoning path from sensor window to recommendation and must reject actions that violate explicit safety constraints.

## Concrete benchmark

The first system is a simulated turbofan engine from NASA C-MAPSS.

- **Development benchmark**: FD001, to validate the complete pipeline with one operating condition and one degradation mode.
- **Final benchmark**: FD004, to test multiple operating conditions and two degradation modes.
- **Recovery data**: generated by the project’s Digital Twin and documented action-transition model, because the public benchmark does not contain action/outcome trajectories.

## Component contracts

### Monitoring agent

Input: normalized telemetry windows.

Output: reconstruction error, anomaly score, and alert state.

Initial model: LSTM autoencoder trained on healthy early-life windows.

### Diagnosis agent

Input: telemetry window and monitoring evidence.

Output: degradation state, fault hypothesis, confidence, and supporting features.

Initial model: interpretable classifier or gradient-boosted model. Supervised fault labels must be documented; they must not be silently inferred from unavailable metadata.

### Prognostics agent

Input: telemetry window, diagnosis evidence, and operating settings.

Output: RUL point estimate, uncertainty interval, and health trajectory.

Initial model: strong classical baseline followed by an LSTM or Transformer only after the baseline is measured.

### Recovery planning agent

Input: estimated state, diagnosis, RUL, candidate actions, and mission constraints.

Output: ranked candidate actions with predicted cost and rationale.

Initial planner: constrained search or optimization. PPO is an optional comparison, not a prerequisite for the first valid result.

### Digital Twin

Input: current estimated state and candidate action.

Output: simulated next state, predicted sensor observations, health trajectory, and failure-risk estimate.

The first twin will be a transparent state-transition surrogate with explicit action effects. Later versions may add learned residual dynamics and uncertainty calibration.

### Safety verifier

Input: current state and simulated outcome.

Output: safe/reject decision, violated constraints, and margin to each constraint.

Safety checks are deterministic and auditable. The language-model or orchestration layer cannot override them.

## Evaluation protocol

- Split by engine unit, never by random rows.
- Fit scalers and feature-selection rules on training units only.
- Keep FD001 development results separate from FD004 final results.
- Compare every advanced model with a simpler baseline.
- Report detection precision/recall and alert lead time, diagnosis macro-F1, prognostics MAE/RMSE, and planner safety-violation rate.
- Include an ablation for the Digital Twin and an ablation for safety verification.
- Preserve random seeds, configuration, model artifacts, and error cases.

## Claim boundary

Until the simulated recovery environment is validated, describe the system as a **Digital-Twin-verified recovery recommendation prototype**, not as a flight-certified autonomous controller.
